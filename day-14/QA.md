# Day 14 — QA & security review

**Scope:** `circuits/secret.circom`, `circuits/secret_naive.circom` (naive on purpose), `contracts/ZkPrize.sol`, `contracts/NaiveZkPrize.sol` (broken on purpose, for the front-running demo), `contracts/SmartWallet.sol`, `src/zk.js`, `src/userop.js`, `scripts/zk-setup.js`. `contracts/verifiers/*.sol` are generated by snarkjs from the keys in `zk/`, and the ERC-4337 `EntryPoint` is the official v0.7.0 npm package. Neither was audited line by line; both are exercised by the tests.
**Method:** tests first (ZK off-chain + on-chain, front-running race, 4337 flows, 2 fuzz properties), then the tools (ESLint, Solhint, `npm audit`, Slither with 102 detectors), then a manual attacker review with the checklist in [`tools/README.md`](../tools/README.md). The main scenario was **"a thief has the owner key: can they get past the daily limit?"**, plus ZK-specific checks: under-constrained signals, field aliasing, proof malleability, front-running, weak secrets, and the trusted setup. Every idea got a test.
**Rounds:** 3. Round 1: 31 tests and the tools. Round 2: manual attacker review, which found **M1** (fixed) and led to 7 more tests. Round 3: everything re-run on the final code after `hardhat clean`.

## Findings

| ID | Severity | Found by | Description | Fix | Proving test |
|----|----------|----------|-------------|-----|--------------|
| M1 | **Medium** | Manual review (thief holds the key) | **The daily limit could be bypassed through gas.** `validateUserOp` pays the gas *prefund* to the EntryPoint **before** `execute` runs, so `_spend()` never sees it. The prefund is `(verification + call + preVerification gas) × maxFeePerGas`, and the signer picks those numbers. A thief sets `maxFeePerGas` so the prefund is ~4.5 ETH and the priority fee to 0. Most of it is left as the wallet's **deposit** in the EntryPoint. Then `execute(entryPoint, 0, withdrawTo(thief, deposit))` moves it out with `value = 0`, which the limit doesn't count. Reproduced before the fix: **4.5 ETH left a wallet with a 1 ETH/day limit, in one block.** The same trick with a high priority fee pays the ETH straight to a thief who is also the bundler. | (1) `validateUserOp` refuses any op whose maximum gas cost is over `MAX_GAS_COST_PER_OP` = 0.01 ETH (`GasCostTooHigh`; the EntryPoint reports `AA23`). (2) `execute` refuses the EntryPoint as a target (`ForbiddenTarget`). Anyone can still top up the deposit with `depositTo`. | `M1`, `M1b`, `M1c`, `an op whose gas budget exceeds the cap…`, `normal gas settings are still accepted…`, fuzz `maxGasCost() matches the EntryPoint's prefund formula` |
| S1 | Info | Slither `reentrancy-events` | `Executed` was emitted after the external call in `execute`. Not exploitable: re-entering `execute` needs `msg.sender` = owner or EntryPoint. | The event is now emitted before the call. A failed call reverts it together with everything else. | 03-wallet tests |
| S2 | Info | Slither `immutable-states` | `guardian` is never changed after the constructor. | Made `immutable` (cheaper reads). Rotating guardians is known issue K2. | — |
| S3 | Info | Slither `arbitrary-send-eth` (×2) | `ZkPrize` / `NaiveZkPrize` send ETH to an address the caller supplies. | Intended. `ZkPrize` pays only the recipient **named inside the proof**. `NaiveZkPrize` is the broken example. | `the same proof with a different recipient is rejected` |
| S4 | Info | Slither `timestamp` (×3) | Daily window and recovery delay use `block.timestamp`. | Intended. A validator can shift time by seconds, which doesn't matter for 1-day and 2-day windows. Timestamps are used only in `execute`/recovery, never in validation (ERC-7562 bans that there). | `resets the next day`, recovery tests |
| S5 | Info | Slither `low-level-calls` (×3), `unused-return` | `.call{value:…}` in `execute` and both prizes. `tryRecover`'s third return value (error argument) is ignored. | Intended. Results are checked, state is settled before each call, and the error argument isn't needed. | `a recipient that refuses ETH…` |
| P1 | Info | Manual pentest (front-running) | Copy a pending claim from the mempool and resend it with a higher fee. | **Naive prize: the copier wins the 1 ETH without knowing the secret.** Safe prize: swapping in your own address → `InvalidProof`. Resending unchanged → Alice is still paid. | 02-frontrun (3 tests) |
| P2 | Info | Manual pentest (under-constrained circuit) | Does `recipient` really bind the proof? | Yes. It is a public input and sits in a real constraint (`recipient * recipient`). Changing it breaks the proof off-chain and on-chain. | `changing any public signal breaks the proof`, `…different recipient is rejected` |
| P3 | Info | Manual pentest (field aliasing) | Public signals are numbers mod the BN254 prime, so `hash + p` "equals" `hash` in the field. | The generated verifier refuses any signal ≥ p. The constructor refuses a lock ≥ p (`HashNotInField`). | `the verifier refuses a public signal ≥ the field prime`, `…a hash outside the field` |
| P4 | Info | Manual pentest (proof malleability) | From any Groth16 proof, `(−A, −B, C)` is a **second valid proof** of the same statement. | Proven valid on-chain. Harmless here because replay protection is the `claimed` flag, never "has this proof been seen". | `proof malleability: (-A, -B, C) is ALSO valid…` |
| P5 | Info | Manual pentest (weak secret) | ZK hides the secret, but the lock `Poseidon(secret)` is public. | A 4-digit PIN was brute-forced in **4,822 tries, 257 ms**. `randomSecret()` uses 248 random bits, and the README warns about this. | `a weak secret is NOT protected by ZK…`, `randomSecret() is always inside the field…` |
| P6 | Info | Manual pentest (4337 validation) | Bad signer, `0x`, short, all-zero, all-`ff` and 64-byte signatures. Replaying a used op. Changing `callData` after signing. Calling `validateUserOp` / `execute` directly. | `AA24` / `AA25` every time. Validation never reverts on a bad signature (`tryRecover`). Direct calls are refused. | 03-wallet "user operations" (7 tests) |
| P7 | Info | Manual pentest (limit logic) | Random sequences of 0–1.2 ETH sends and 0–2-day jumps; raising the limit with the owner key. | No calendar day ever sends more than the limit (25 random runs). The owner can only lower the limit; raising needs the guardian. | fuzz property 1, `the owner can only LOWER the limit…` |
| P8 | Info | Manual pentest (DoS on the prize) | A recipient contract that refuses ETH. | The whole claim reverts (`TransferFailed`), `claimed` stays false, and the prover can claim again for another address. | `a recipient that refuses ETH…` |

### Known issues (accepted, with reasoning)

| ID | Description | Why it stays |
|----|-------------|--------------|
| K1 | **A thief with the key can still burn up to 0.01 ETH of gas per operation**, and can send many operations a day. The cap limits the loss per op, not per day. | A per-day gas budget would need time in validation, which ERC-7562 forbids. The real defence is the guardian (K3) plus a production idea: count gas spent in `execute` on the next op. Loss per op is bounded and visible on-chain. |
| K2 | **The guardian can't be changed** (immutable), and one guardian is a single point of trust. | Keeps the lesson small. Production wallets use M-of-N guardians with a delay on changing them. |
| K3 | **During a recovery, whoever holds the owner key can cancel it.** That includes a thief. | That is the classic trade-off: if the guardian could not be stopped, a malicious guardian could steal the wallet. With one guardian and one key, one side must win. The daily limit caps the damage meanwhile. Fix in production: M-of-N guardians whose recovery the single key cannot cancel. Pinned by test `K3`. |
| K4 | **One-person trusted setup.** `scripts/zk-setup.js` runs both Groth16 ceremonies with one contributor. Whoever knows the random "toxic waste" can forge proofs. | Fine for learning, never for money. Production: a multi-party ceremony (one honest participant is enough), or PLONK with a universal setup. |
| K5 | **No factory / `initCode`**, so wallets are deployed directly instead of counterfactually. **No paymaster** in the tests. | Kept the 4337 part focused on validation and limits. `maxGasCost()` already returns 0 when a paymaster pays. |
| K6 | **The limit covers ETH only.** Tokens moved with `execute(token, 0, transfer(...))` aren't counted. | Today's wallet holds ETH. A token limit needs per-token accounting (one `_spend` per token). |
